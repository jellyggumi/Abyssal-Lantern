## 1. 가독성 → 보상 지각: 연결은 실재한다. 크기를 잰다.

### 1.1 병사는 이미 보상 이벤트를 생산한다 [OBSERVED]

`design/core-loop.md:16`이 정의하는 Loop 1의 보상 이벤트는
*"Block collapse chain (BFS) + damage callouts + core HP delta"* 다.
그 계측 진입점은 하나다:

```
DestructibleBlock.cs:408   if (!isGroundAnchor) TelemetrySink.BlockDestroyed(collapseChainDepth);
```

**그 진입점에 도달하는 경로가 발사만이 아니다.** 병사 근접 공격이 같은 곳에 닿는다:

```
UnitController.cs:1070-1075
  var block = target.GetComponent<DestructibleBlock>();
  if (block != null)
  {
      if (unitType == UnitType.Knight) damage *= 1.8f;   // :1073
      block.TakeDamage(...);                             // :1074 → DestructibleBlock:408
  }
```

**즉 병사는 이미 1급 보상 생산자다.** 그런데 플레이어는 그 채널을 못 읽는다.

### 1.2 그 채널의 크기 — 모델이 아는 전량의 7.30배 [OBSERVED 상수 + INFERENCE 산술]

| 기호 | 값 | 근거 |
|---|---|---|
| 근접 기본 피해 | 20.0 | `UnitController.cs:56` `attackDamage = 20f` |
| 공격 쿨다운 | 1.5 s | `UnitController.cs:58` `attackCooldown = 1.5f` |
| 기사 블록 배수 | ×1.8 | `UnitController.cs:1073` |
| 버프 배수 (평시) | 1.0 | `UnitController.cs:131` `damageMultiplier = 1.0f` |
| 턴 평균 초 s | 7.5 | `MatchLengthModel.cs:45` |
| 모델 턴당 피해 d | 37.0 | `MatchLengthModel.cs:51` |

기사 콤보는 6타 주기다 — 6번째 3타, 3번째 2타, 그 외 1타
(`SiegeTactics.cs:101-104`, `Assets/Editor/AosOverhaulTests.cs:18-25`가 고정).

```
타당 평균     = (1+1+2+1+1+3) / 6              = 1.50 타/스윙
타당 피해     = 20.0 × 1.0 × 1.8               = 36.0 HP
스윙당 피해   = 36.0 × 1.50                    = 54.0 HP
턴당 스윙     = 7.5 / 1.5                      = 5.00
──────────────────────────────────────────────────────────
기사 1명 접촉 유지 시                          = 270.0 HP / 턴
                                    d(37) 대비 = 7.30 배
```

접촉률로 할인해도 크기가 남는다:

| 턴 중 접촉 비율 | 턴당 HP | d 대비 |
|---|---|---|
| 100 % | 270.0 | **7.30 ×** |
| 50 % | 135.0 | **3.65 ×** |
| 25 % | 67.5 | **1.82 ×** |
| **13.7 %** | **37.0** | **1.00 ×** ← 손익분기 |
| 10 % | 27.0 | 0.73 × |

> **기사 한 명이 턴의 13.7%만 벽에 붙어 있으면 모델이 아는 피해 전량과 같아진다.**
> 접촉률은 미측정이므로 위 표는 밴드다. 결론은 밴드 어디서도 같다 — 이 채널은
> 무시할 수 있는 크기가 아니다. `[INFERENCE — 접촉률 미측정]`

### 1.4 F-1 — 리드백이 병사 전과를 발사 전과로 청구한다 [OBSERVED]

이번 사이클이 `ShotReadback.Compose`에 소유 구분을 넣었다. 그 개선은 유효하다.

```
                                        bool? wallOwnerIsPlayer = null)   ← 공격자 인자 없음
  { if (!shotOpen) return; ... }

DestructibleBlock.cs:431   ShotTraceDirector.NoteBlockDestroyed(kind, owner);   ← 공격자 미전달
```

그리고 `Seal()`은 **모든 body가 해소된 뒤** 발행된다:

```
ShotTraceDirector.cs:241-244
  "Called at the settle boundary in GameManager.WaitAndEndTurn — after every body

```

**결과**: 3턴 전에 착지해 지금도 벽을 때리고 있는 기사의 파괴가, 이번 턴 발사의 전과로

| | 실제 | 플레이어가 읽는 것 |
|---|---|---|
| 원인 | 발사 + 3턴 전 기사 + 대포 | **발사 하나** |
| 크기 | 최대 7.30배 부풀려짐 (§1.2) | 자기 조준이 좋았다고 학습 |

**플레이어가 자기 조준을 평가할 수 있는 유일한 피드백 채널이 병사 전과로 오염돼 있다.**
`aim-space-reachability.md:§0`이 잰 "61.0% 성벽 앞 미달"과 이 리드백이 동시에 참일 수
있는 이유가 여기 있다 — 빗맞은 발사도 병사가 일하는 동안에는 성과를 보고받는다.

그리고 라벨 위치가 이 문제를 굳힌다: `SMASH`/`HIT`이 `target.position`에 뜬다
(`UnitController.cs:1062`). 기사 셋이 같은 블록을 때리면 라벨 셋이 같은 자리에 겹친다 —
**몇 명이 기여하는지 셀 수 없다.**

### 1.5 그런데 왜 이게 밴드를 안 흔드는가

**병사 행동 가독성은 플레이어의 어떤 결정에도 입력되지 않는다.** 출하 설정에서:

```
DeploymentController.cs:146   SelectedCard = DeployCard.Cannon;   ← 원샷 모드 강제 고정
DeploymentController.cs:173   "No AI deployment in the one-shot loop: the enemy turn is its shot."
```

Knight / Archer / Barrel은 원샷 모드에서 **구매 불가**다. 병사는 발사로만 전장에 오고,
착지 후에는 자율이다 — 재지시·회수·표적 변경 입력면이 **0개**다.

| 플레이어가 병사에게 할 수 있는 것 | 존재 |
|---|---|
| 발사로 투입 | ✅ 턴당 1회 |
| 표적 지정 | ❌ `FindTarget()` 자율 (`UnitController.cs:850`) |
| 이동 지시 | ❌ `AdvanceTowardEnemyCamp()` 자율 (`:828`) |
| 회수·철수 | ❌ 경로 없음 |

**결정에 입력되지 않으므로 승률 축을 움직이지 않는다.** 이것이 세 밴드가 전부 불변인
구조적 이유다. 가독성은 **결과의 설명**이지 **선택지의 확장**이 아니다.

> [!important] 단 하나의 예외 경로가 있다 — §4가 다룬다
> 리드백 오귀속(§1.4)이 제거되면 플레이어의 자기 조준 평가가 정확해진다.
> 조준 학습이 달라지면 조준 품질이 달라지고, **조준 품질은 승률에 매우 민감하다**
> (+0.01 → +11%p, `qa/evidence/g2-winrate-measurement.txt`).
> 이것은 밴드 위반이 아니라 **측정 순서 제약**을 만든다.

### 2.1 밴드 ① — comeback (일발역전) ≤ 30% per activation

```
  EndGame(zoneOwnedByPlayer ? "KEEP SEIZED — DEFEAT!" : "CASTLE SEIZED — VICTORY!");

```

```
물량 경로 = 1585 / 37            = 42.8 턴
──────────────────────────────────────────
점령이 54 배 빠르다.
```

|---|---|---|

> [!warning] 정직한 구분 — 가독성이 이 채널을 만들지 않았다
> 점령 게이지는 **연출이 있다** — 링 색 보간(`CaptureZoneController.cs:67-69`),
> 퍼센트 라벨(`:144`), 50% 경보(`:97-99` `SiegeAlarmSystem.Post`), 충격파 펄스(`:89-91`).
> 즉 **효과는 보인다.** 안 보이는 것은 **병사가 왜 진영으로 걸어가는가(의도)**다.
> 이 채널은 가독성 작업 전에도 있었고, 가독성 조사가 그것을 **드러냈을 뿐**이다.
> **밴드를 흔드는 것은 가독성 변경이 아니라 이 미계상 채널이다.**

**공정성 축은 안 기울어진다** — 존은 양측 코어에 대칭으로 생성되고
(`GameManager.cs:733-734`), 승패는 소유측 기준으로 갈린다(`:738-741`).
적 병사도 같은 규칙으로 내 진영을 점령한다. **밴드 위반이 아니라 커버리지 공백이다.**

→ **D-6 (디렉터 결정)**: 점령 채널을 G5 ① 측정 범위에 포함할 것인가.
게이트 정의 범위이므로 PM 권한 밖이다. **PM 의견은 포함**이다 — 문구가

## 4. 밸런스 감사의 보류 결정 — 유효하다. 순서 제약이 하나 붙는다.

### 4.1 보류를 뒤집지 않는다

`qa/balance-and-level-design-audit.md:11-14`: *"지금 밸런스를 조정하면 안 된다 —
`EffectiveDamagePerTurn = 37`은 검증된 적이 없다."*

가독성 변경은 **밸런스 수치 변경이 아니다.** `d`는 발사 채널 항이다:

```
MatchLengthModel.cs:20-21   d = "effective damage landed per turn — on-target damage only"
MatchLengthModel.cs:47-50   "Retuned 42 → 37 alongside the tempo pass (baseShotDamage 120 → 106)"
```

가독성 표시는 `d`(37) · `s`(7.5) · `M`(1585) 중 무엇도 건드리지 않는다.
**→ 보류의 적용 대상 밖이다.**

### 4.2 오히려 보류 근거를 강화한다

감사는 *"37이 어떤 명중률을 전제하는지 아무도 재지 않았다"*(`:33`)까지 갔다.
§1.1~1.3이 한 겹 더 얹는다:

```
모델:  M = b·h + c ,  N = M / d          (MatchLengthModel.cs:13-14)
실제:  병사 근접도 성벽을 부순다          (UnitController.cs:1070-1075, 기사 ×1.8)
실측:  파괴량이 모델의 2.93 ~ 8.31 배     (§1.3, 재질 가정 범위)
```

**`d`의 명중률 전제가 미검증인 것만이 아니라, 모델에 병사 항이 아예 없다.**
보류를 흔들지 않고 **더 정당화한다.**

→ 감사의 재측정 목록(`:113-116`)에 항목 추가 권고:
**"병사 근접 채널의 턴당 성벽 피해"** — 없으면 `d`를 검증해도 총 피해의 일부만 설명한다.

### 4.3 흔드는 것은 하나 — 측정 순서

경로: 리드백 오귀속(§1.4) 제거 → 플레이어의 자기 조준 평가가 정확해짐 →
조준 학습 변화 → **조준 품질 변화**.

그리고 `d`는 조준 품질의 함수다(`MatchLengthModel.cs:20-21` "on-target damage only").
조준 민감도는 매우 높다 — **+0.01 → +11%p**(`qa/evidence/g2-winrate-measurement.txt`).

```
가독성 변경 전에 잰 d  ≠  가독성 변경 후에 잰 d
```

**보류 중인 `d` 측정(B1)은 가독성 변경보다 먼저 기준선을 떠야 한다.**
나중에 `d`가 움직였을 때 "가독성→학습→조준" 때문인지 "원래 37이 틀렸다" 때문인지
분리할 방법이 없어진다. 비용은 거의 0이고, 놓치면 복구 불가다. → **N-21.**

### 4.4 요약

| 질문 | 답 |
|---|---|
| 가독성 변경이 보류 결정을 뒤집는가 | **아니다.** `d`·`s`·`M` 미변경 → 적용 대상 밖 |
| 보류 근거를 약화하는가 | **아니다. 강화한다** — 모델에 병사 항이 없다(§4.2) |
| 무엇이라도 흔드는가 | **순서 하나.** `d` 기준선을 가독성 변경 **전에** 뜨거나, 최소한 측정 기록에 변경 커밋 해시를 병기해야 한다(§4.3, N-21) |

## 10. 개정 r3 — designer 회신 반영: 금지 목록 위반 2건 접수 (2026-08-14)

`DesignerVisibility`가 **이미 출하 중인 명멸 위반 2건**을 신고했고 QA(`QaVisibility`)가 종료돼

> 이 두 건은 이번 사이클 금지 목록(`design/graphics-needed.md` §D, "초당 3회 초과 명멸")
> 위반이다. **가독성 작업이 만든 것이 아니라 선재 결함**이며, 조사가 드러냈다 — F-2(점령

### 10-A. U-12 — 버프/디버프 만료 명멸. designer가 **과대**했다.

```
UnitController.cs:1421   float blink = 0.5f + 0.5f * Mathf.Sin(Time.time * 22f);
호출:  :767 (버프, 잔여 ≤0.8s) / :777 (디버프, 잔여 ≤0.8s)
```

> **r6-b: 이 인용은 측정 시점(수정 전) 스냅샷이다.** 현재 `:1424`는 `22f` 대신
> `AccessibleBlink.SafeSineFrequency`(= 2.6 × 2π = 16.34, **2.60 Hz**)를 쓰고,
> 값이 가는 곳도 `sr.color`가 아니라 `SetStatusTint(tintColor, 0.55f * blink)`
> — **틴트 가중치**다(`:1425`, `UnitSpriteAnimator.cs:273-276`).
> **U-12는 종결됐다**: 3.501 Hz → 2.60 Hz(안전선 정확히, 하드 한계의 0.87배).
> 아래 분석은 결함이 있던 시점의 기록으로 읽을 것.

designer는 **8Hz**로 신고했다. 그것은 **주석(`:765`)의 값**이고 코드는 다르다:

```
각속도 22 rad/s  →  f = 22 / 2π = 3.501 Hz
주석 8Hz 대비 코드는 1/2.28 배  →  주석과 코드가 어긋나 있다
WCAG 2.2 SC 2.3.1 한계 3.0 Hz  →  위반, 한계의 1.17 배
0.8초 창 안 명멸 횟수 = 2.80 회
```

| | designer 신고 | 실측 (코드) |
|---|---|---|
| 주기 | 8.00 Hz | **3.501 Hz** |
| 한계 대비 | 2.67 배 | **1.17 배** |
| 판정 | 위반 | **위반 (유지)** |

**결론은 안 바뀐다 — 여전히 위반이다.** 다만 **한계를 겨우 넘는다**(1.17배).
그리고 **주석이 코드보다 2.28배 크게 적혀 있다** — 이번 사이클이 이미 두 번 만난 병이다
(궤적 아크 "의도는 주석에만", 적 조준 0.9초 창). **주석을 코드에 맞춰 고쳐야 한다.**

### 10-B. U-13 — 도화선 명멸. designer가 **과소**했다. 이쪽이 심각하다.

> [!warning] **이 절의 수치는 r4(§11-A)가 정정했다.** 아래 `dφ/dt / 2`는 **순간 도함수**이고
> WCAG의 측정량이 아니다. WCAG SC 2.3.1은 **1초 창당 명멸 수**를 센다. 올바른 값은
> **수정 전 최악 1초 창 9.00 /s = 한계의 3.00배**(11.50 /s·3.83배가 아니다).
> 아래 표는 **내가 어떻게 틀렸는지의 기록으로만** 읽을 것. 위반이라는 결론은 유지된다.

```
UnitController.cs:1273   float blink = Mathf.PingPong(t * (3f + t * 5f), 1f);
```

`PingPong(x,1)`은 x가 2 나아갈 때 1회 왕복(= 1 명멸)이다. 위상은 φ(t) = 3t + 5t²이므로

```
dφ/dt = 3 + 10t          ← t² 항의 미분이 10t다. (3+5t)가 아니다.
명멸률 = (3 + 10t) / 2
```

~~designer는 `(3+5t)/2`를 썼다 — `t·(3+5t)`의 괄호 안 계수를 도함수로 오독했다.~~
**r4: 미분 자체는 내가 맞았지만(dφ/dt = 3+10t) 그 값은 WCAG의 측정량이 아니다.**
아래 "실측" 열은 **순간 도함수**이고 명멸률이 아니다 — **열 이름이 틀렸다.**

| t | designer 값 | 내 값 = **순간 도함수** (≠명멸률) | 비고 |
|---|---|---|---|
| 0.0 s | 1.50 /s | 1.50 /s | — |
| 0.5 s | — | 4.00 /s | — |
| 1.0 s | 4.00 /s | 6.50 /s | — |
| 2.0 s (기폭) | 6.50 /s | 11.50 /s | ~~3.83배~~ → **§11-A: 올바른 값은 1초 창 9.00 /s = 3.00배** |

```
위반 개시:   3 + 10t > 6   →  t > 0.30 s      (designer 계산은 0.60 s — 2배 늦다)
도화선 길이: 2.0 s                            (SiegeTactics.cs:98 BarrelFuseSeconds)
위반 구간:   1.70 s = 도화선의 85 %
총 명멸:     φ(2)/2 = 26/2 = 13.0 회 / 2초    (평균 6.50 /s)
```

> [!warning] ~~designer 신고보다 나쁘다~~ → **r4에서 이 판단을 철회했다 (§11-A)**
> ~~최고 명멸률이 11.50/s로 한계의 3.83배이고 designer가 적은 6.50/s는 평균값이다.~~
> **내가 단위를 잘못 썼다.** 순간 도함수를 "명멸률"이라 불렀고, WCAG는 1초 창을 센다.
> designer에게 "네 값은 평균이지 최고값이 아니다"라고 되돌려준 지적을 **철회한다.**
> 여전히 유효한 것: **위반이다**(9.00/s = 한계 3.00배), 도화선 **85%가 위반 구간**,
> 그리고 **U-12(S3)와 U-13(S2)을 같은 등급으로 묶으면 안 된다** — 노출량 근거(§10-C)는 불변.

## 11. 개정 r4 — 내 측정법이 틀렸다. designer가 잡았다. (2026-08-14)

`DesignerVisibility`가 §10-B의 **측정 단위 자체**를 정정했다. 검증했고 **그들이 맞다.**
그리고 내 틀린 수치가 **이미 출하 코드 주석에 박혀 있다** — 그것까지 내 책임이다.

### 11-A. WCAG는 순간 도함수가 아니라 **1초 창당 명멸 수**를 센다

§10-B에서 나는 `dφ/dt / 2`를 "명멸률"로 썼다. **그것은 순간 기울기이고 WCAG의 측정량이
아니다.** SC 2.3.1은 *어떤 1초 창 안의 명멸 수*를 센다. 0.14초짜리 3.70/s 스파이크는
어떤 1초 안에도 3.70회를 만들지 못한다.

실제 `Mathf.PingPong` 출력의 방향 반전을 세어 재측정했다(미분 없이, 지상 진실).
**명멸 1회 = 명암 1쌍**이므로 반전 수 ÷ 2 — 이 규약은 `AccessibleBlink.cs:43-44`가
*"completes one light-dark pair per 2 units of phase"* 로 직접 적고 있다.

| 버전 | 최악 1초 창 | 한계(3.0) 대비 | 안전선(2.6) 대비 |
|---|---|---|---|
| 수정 전 `3+5t` (출하돼 있던 것) | **9.00 /s** | **3.00 배** | 3.46 배 |
| **현재 출하된 clamp 수정** | **3.00 /s** | **1.00 배** | **1.15 배** |
| `k=0.55` (도함수 경계형) | 2.50 /s | 0.83 배 | 0.96 배 |

**내 §10-B 수치 정정:**

| | r3 (내 값) | r4 (올바름) |
|---|---|---|
| 수정 전 최악 | 11.50 /s = 3.83배 | **9.00 /s = 3.00배** |
| 성격 | 순간 도함수 | **1초 창 실측** |
| 방향 | **과대** | — |

> **위반이라는 결론은 안 바뀐다** — 9.00/s는 여전히 한계의 정확히 3배다.
> 바뀐 것은 크기(3.83 → 3.00배)와 **그 수치를 뭐라고 불러야 하는가**다.
> designer가 신고할 때 내가 "네 값은 평균이고 최고값이 아니다"라고 되돌려준 것은
> **내 쪽이 단위를 잘못 쓴 상태에서 한 지적**이었다. 그 부분을 철회한다.

### 11-B. 내 오류가 출하 코드 주석에 전파됐다

```
AccessibleBlink.cs:15-19
  /// What was found shipping (`_workspace/current/pm/legibility-retention-note.md`):
  /// - the barrel fuse peaked at **11.50 flashes/s**, 3.83x the ceiling, ...
```

**이 파일이 내 문서를 출처로 인용하면서 내 틀린 수치를 옮겨 적었다.**
`UnitController.cs:1275-1276`의 주석도 같다.

→ **수정 요청**: 두 주석의 `11.50 flashes/s, 3.83x`를 **`9.00 flashes/s, 3.00x
(worst 1-second window)`** 로 고칠 것. 단위 명시(`worst 1-second window`)를 함께 넣어야
같은 오독이 재발하지 않는다. **이번 사이클이 네 번째로 만나는 주석/실제 불일치**이고,
이번에는 **내가 원인이다.**

### 11-C. 진짜 결함은 위반이 아니라 **마진 0**이다

현재 출하된 clamp 수정의 최악 1초 창이 **정확히 3.00/s** — 표준의 하드 한계선이다.
그런데 같은 파일이 왜 그러면 안 되는지를 직접 적어놨다:

```
AccessibleBlink.cs:33-36
  "a frame-rate spike, a hitch, or a `Time.deltaTime` outlier can push an on-the-line
   rate over it. Sitting at exactly 3.0 would make compliance depend on frame pacing."
```

**선언한 여유 13%(= 2.6/3.0)가 실측으로는 0%다.** 자기 상수(`SafeFlashesPerSecond = 2.6`)
대비로는 **1.15배 초과**다. 즉 코드가 **자기 안전선을 넘고 하드 한계에 정확히 앉아 있다.**

**원인 [OBSERVED]**: clamp가 **위상률**에 걸려 있는데 명멸률은 **`t × 위상률`의 도함수**다.
`UnitController.cs:1281`이 `PingPong(t * AccessibleBlink.FusePhaseRate(t), 1f)`를 넘기므로
`FusePhaseRate`를 5.2로 묶어도 **`t` 배가 남는다.**

```
φ(t) = t · min(3+5t, 5.2)
순간 피크(좌극한) = (3 + 10·0.44)/2 = 3.7000 /s   ← 하드 1.23배, 안전선 1.42배
                    clamp 개시점은 3+5t=5.2 → 정확히 t=0.44
```

**r4-b: 처음 적은 `3.69`는 격자 스캔 인공물이었다. 정확값은 3.7000이다**(designer 지적).

**두 단위를 함께 둔다 (N-24 규약)** — 어느 쪽도 단독으로는 결함을 다 설명하지 못한다:

| 버전 | 순간 피크 | 1초 창 | 순간 여유 | 창 여유 |
|---|---|---|---|---|
| 수정 전 `3+5t` | 11.50 /s | **9.00 /s** | −283 % | **−200 %** |
| **출하 clamp (현재)** | **3.70 /s** | **3.00 /s** | **−23 %** | **0 %** |
| `k=0.55` (권고) | 2.60 /s | 2.50 /s | **+13 %** | **+17 %** |

**창값은 "위반인가"를 답하고, 순간값은 "여유가 있는가"를 답한다.**
출하 clamp는 창값으로 **한계선에 정확히 앉고**(0%), 순간값으로는 **이미 넘는다**(−23%).
U-14의 근거는 순간값 쪽이다 — 창값만 보면 "한계 준수"로 읽혀 마진 미달이 안 보인다.

### 11-D. 새 테스트가 코드가 생산하지 않는 양을 재고 통과한다

```
AccessibleBlinkTests.cs:49
  float rate = AccessibleBlink.PingPongFlashRate(AccessibleBlink.FusePhaseRate(t));
                                                 └─ 위상률 min(3+5t,5.2)
  코드가 만드는 것: d[t · min(3+5t,5.2)]/dt / 2
```

검증한 격차 — **모든 값에 단위를 병기한다(N-24)**:

| t | 테스트가 주장 | 코드가 생산 (순간, 좌극한) | |
|---|---|---|---|
| 0.00 s | 1.50 /s | 1.50 /s | 일치 |
| 0.20 s | 2.00 /s | **2.50 /s** | 격차 |
| **0.44 s** (clamp 개시) | **2.60 /s** | **3.70 /s** | **격차 — 하드 한계 3.0 초과 (1.23배)** |
| 0.50 s 이후 | 2.60 /s | 2.60 /s | 일치 |

> [!warning] **r4-b 정정 — 내가 처음 적은 `3.15 /s`는 실재하지 않는 값이다**
> designer가 재현에 실패해 추적했고 **원인을 찾았다: 중앙차분이 clamp 꺾임을 가로질렀다.**
> clamp 개시점은 `3+5t = 5.2` → **정확히 t = 0.44**이고, 내가 그 점에서 중앙차분을 쓰는 바람에
> **좌측 기울기 3.70과 우측 기울기 2.60이 평균돼 (3.70+2.60)/2 = 3.15**가 나왔다.
> **어떤 창에서도 나오지 않는 수치 인공물이다.** 좌극한 **3.70 /s**가 참값이다.
> 같은 이유로 §11-C의 `3.69`도 격자 스캔 인공물이었다 — **정확값은 3.7000**이다.
> **판정은 더 강해진다**: 테스트 2.60 vs 실제 **3.70**(하드 1.23배). designer 지적이 옳다.

**테스트가 통과하는데 코드가 t=0.44s에서 하드 한계를 1.23배 넘는다.**

> [!warning] 무테스트보다 나쁘다
> 이 테스트는 안전을 **인증한다.** N-23("명멸 주기를 상수+테스트로 고정")의 취지는
> 맞았지만 **재는 양을 지정하지 않아 잘못된 양을 재는 테스트가 통과했다.**
> N-23을 정정한다 — 아래 N-23′.

### 11-E. 내가 준 밴드가 designer 것보다 나빴다

§10-C 회신에서 나는 `k=0.75`를 상한으로 제시했다. designer는 `k=0.55`를 권고했다.
도함수 기준으로 재보면:

```
피크 = (3 + 2k·t)/2  at t=2.0  =  (3 + 4k)/2
k=0.75 → 3.00 /s   = 하드 한계 정확히, 여유 0 %      ← 내 제안
k=0.55 → 2.60 /s   = 자기 안전선 정확히, 여유 13 %   ← designer 제안
```

**designer의 0.55가 옳다.** 내 0.75는 §11-C가 지적한 "정확히 3.0에 앉는" 실수를
**한 번 더 반복하는** 값이었다. 수용한다.

### 11-F. 공 귀속 정정 — F-4 수정은 designer가 한 것이 아니다

`messages/002-game-designer.md` 둘뿐이다(파일 확인). `git diff`를 보고 **동시에 실행 중인
레인이 designer뿐이라고 가정**한 것이 오류다.

### 12-B. L-1/L-2 — designer의 "적용 불가"는 표현이 약하다. **실제로는 기하학적 모순이다.**

designer의 IRC 요약("월드 라벨 적용 불가")보다 그들 문서(`design/unit-action-legibility.md:271-280`)의
논증이 훨씬 강하다. 전 수치를 재현했다 `[OBSERVED 상수 + INFERENCE 산술]`:

```
병사 몸높이 = 1.15u                    (UnitController.cs:86 bodyWorldHeight)
환산       = 1.90pt → 2.29px (최악 줌)  (qa/unit-action-legibility-measurement.md:315)
           = 1.2053 px/pt
```

| 요구 | 필요 fontSize | 라벨 월드 높이 | 병사 대비 |
|---|---|---|---|
| **L-1** (최악 줌 em ≥ 12px) | **9.96** | 0.996u | **0.87 ×** |
| **L-2** (0.75× 바운스 저점도 통과) | **13.28** | 1.328u | **1.15 ×** |
| 종속 표기 상한 (병사의 50%) | **≤ 5.75** | 0.575u | 0.50 × |

```
모순 = 9.96 / 5.75 = 1.73 배        ← designer 신고 1.73배와 정확히 일치
L-2에서 라벨 높이 1.328u > 병사 1.15u  ← 주석이 주석 대상보다 커진다
```

**즉 문제는 "측정 불가"가 아니다 — QA가 측정했고 나도 재현했다.**
거짓인 것은 floor의 **암묵 전제**다:

> **고정 px 하한은 "라벨 크기가 주석 대상과 무관하게 정해질 수 있다"를 가정한다.**
> UI 캔버스 텍스트에서는 참이다 — HUD는 월드 기하와 경쟁하지 않는다.
> **월드 라벨에서는 거짓이다** — 1.15u 몸에 붙은 라벨을 최악 줌에서 12px로 올리면
> 라벨이 병사의 0.87~1.15배가 된다. **주석이 주체가 된다.**

### 12-C. 그래서 이 모순의 해소는 게이트 완화가 아니다 — **채널 이동이다**

세 선택지를 놓고 본다:

| 안 | 결과 | 판정 |

그리고 **designer의 안 1이 이미 이 모순을 우회한다** — 내 레인의 관점에서 이게 핵심이다:


**정보를 라벨 채널에서 빼면 라벨이 하한을 짊어질 필요가 없어진다.** designer가
`fs=5.0`(최악 줌 6.03px, floor의 1.99배 미달, 현재 대비 2.63배 개선)을 **통과로 표기하지
않은 것은 정직하다** — 그리고 안 1이 있으면 그 라벨은 **판독의 주 경로가 아니므로**
미달이 치명적이지 않다.

> [!important] 내 레인의 판정
> **L-1/L-2는 "완화"가 아니라 "적용 대상 축소"로 정정해야 한다** — 라벨이 **단독으로
> 판독을 책임지는 경우**의 하한으로 좁히고, 지속 상태가 애니메이션으로 이전된 뒤에는

> 이렇게 하면 U-1이 **은폐되지 않고 해소된다** — 2.29px → 6.03px(2.63배)로 개선되고,
> 그 라벨이 더 이상 유일한 판독 경로가 아니게 된다.
> **이것은 게이트 정의 변경이므로 디렉터 권한이다.** PM 의견은 위와 같다.
