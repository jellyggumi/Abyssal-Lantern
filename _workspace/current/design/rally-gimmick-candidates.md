### 1.2 법칙 1 — 시간 예산은 **비대칭**이다

```
T = 21.42 · C          (C = 사이클 길이)
상한: C ≤ 330/21.42 = 15.406  →  ΔC ≤ +0.41 s
하한: C ≥ 270/21.42 = 12.605  →  ΔC ≥ −2.40 s
```

> **내 사이클을 늘리는 데 쓸 수 있는 예산은 0.41초뿐이고, 줄이는 쪽은 2.40초 있다.**
> 5.9배 비대칭이다. "생각할 거리를 더 준다"는 제안은 거의 전부 이 0.41초에서 죽는다(C4).

### 1.3 법칙 2 — 자재 환율

```
1 HP = s/d = 7.5/37 = 0.2027 초
ΔT = 0.2027 · ΔM
상한: ΔT ≤ +8.7 s  →  ΔM ≤ +42.9 HP   (반올림 +43)
하한: ΔT ≥ −51.3 s →  ΔM ≥ −253 HP
```

> **방어를 주는 기믹은 판당·진영당 +43 HP까지만 순증할 수 있다.**
> 게임에서 가장 작은 블록이 Wood 30 HP다. **판당 Wood 1.4개**가 전부다.
> `BrickPlacementController.cs:24`의 기본값은 Stone(85 HP) — 1개만 놔도 예산의 2배다.

**이 법칙의 유일한 탈출구가 ΔM = 0, 즉 자재 보존이다.** 방어를 주되 그만큼 성벽에서
떼어내면 예산을 아예 쓰지 않는다. C1과 C2가 이 경로를 쓴다.

### 1.4 법칙 3 — 공정성 예산은 페이싱보다 좁다 (PM 레인 협업)

`_workspace/current/qa/evidence/g2-winrate-measurement.txt` [OBSERVED]:

조준 +0.01 → 승률 49.0% → 60.0%   (+11 pp, 선공 교대 계열)
조준 +0.01 = 피해 +1.06/발 × 공격 턴 19.4 = 누적 +20.6 HP

| 공정성 (승률 ±5 pp 권장) | **9.4 HP/판** | **비대칭**일 때만 |
| 공정성 (승률 ±10 pp 상한) | 18.7 HP/판 | 비대칭일 때만 |

> **대칭이면 공정성 예산은 사라지고 페이싱 43만 남는다. 비대칭이면 9.4가 구속한다.**
> `BrickPlacementController`에 AI 경로가 0줄이라는 사실(§4.1.4)이 정확히 이 스위치다.

### 1.5 유휴 항등식 — 새 식 유도

기존 항등식 `유휴 = 1 − D/15`는 **적 턴에 열리는 창(w)을 담을 항이 없다.**
분모 15가 상수로 굳어 있어 그대로 쓰면 어떤 적 턴 기믹도 0 pp로 계산된다.
사이클을 항으로 다시 쓴다.

```
사이클 C = (D + ΔD) + tail_P + 0.9 + tail_A + Δ            [tail_P = tail_A = 4.22]
         = (D + ΔD) + 9.34 + Δ

조작 가능 시간 = (D + ΔD) + w_P + w_A

        ┌                                             ┐
유휴 =  │ 1 −  ─────(D + ΔD) + w_P + w_A─────          │
        │        (D + ΔD) + 9.34 + Δ                   │
        └                                             ┘

  w_A ∈ [0, 5.12]   적 턴 안에 여는 창 (적 턴 전체 길이가 상한)
  w_P ∈ [0, 4.22]   내 발사 후 꼬리 안에 여는 창
  ΔD               조준 시간 변화 (분자·분모 동시 증가 → 효율 낮음)
  Δ                사이클에 추가되는 순수 대기 (법칙 1: ≤ +0.41)
```

**검산**: w = ΔD = Δ = 0 → 유휴 = 1 − 5.67/15.01 = **62.2%** ✓ 기존 값 재현.
w_A = 5.12, w_P = 4.22 → 유휴 = 1 − 15.01/15.01 = **0%** (명목상 포화).

**이 식이 말하는 것**: w는 분자만 키우고 분모는 안 건드린다 → **적 턴 창은 유휴 저감
효율이 1.0**이다. ΔD는 분자와 분모를 같이 키운다 → 효율이 0.38로 떨어진다.
**적 턴에 여는 것이 내 턴을 늘리는 것보다 2.6배 효율적이다.**

### 1.6 지표 2종 — 명목과 실효

위 식의 w는 "입력이 코드에서 차단되지 않는가"다(정본 `idle-time-measurement.md` §1의 정의).
그런데 **창이 열린 것과 결정을 요구하는 것은 다르다.** 두 지표를 따로 낸다.

| 지표 | 정의 | 등급 |
|---|---|---|
| **명목 유휴** | 입력 창이 닫혀 있는 시간 비율 (위 식 그대로) | 코드 정의 — 재현 가능 |
| **실효 유휴** | 플레이어가 실제로 결정에 쓰는 시간을 뺀 비율 | `[INFERENCE]` — QA 실측 필요 |
| **결정 밀도** | 커밋 가능한 결정 / 분 | 계산값 |

기준: 결정 밀도 = (21.42 발사 + 1 Last Stand) / 321.3 s × 60 = **4.19 회/분**.
피카츄 배구는 1.12초마다 타구이므로 **53.6 회/분** — 12.8배다.

## 3. 공통 전제 3가지

### 3.1 "적 턴에 여는 것은 공짜, 내 턴을 늘리는 것은 0.41초"

§1.5의 효율 비교와 §1.2의 비대칭 예산이 합쳐진 결론이다.
**적 턴 창(w_A)은 사이클을 안 건드리므로 페이싱 비용이 정확히 0**이고,
**"더 생각할 거리"(ΔD)는 0.41초 예산에서 즉시 죽는다.**
이것이 C1·C7이 위에 오고 C4가 아래에 있는 이유다.

### 3.2 자재 보존이 유일한 방어 설계 경로

법칙 2가 허용하는 순증은 판당 Wood 1.4개다. 기믹이 될 수 없는 양이다.
따라서 **방어를 주는 모든 후보는 그만큼을 성벽에서 떼어내야 한다**(ΔM = 0).
이때 페이싱 예산과 공정성 예산을 **둘 다 쓰지 않는다.**

### 3.3 D4는 유휴를 못 줄인다 — 정직한 사전 경고

과제가 D4를 요구했고 §4.3에 설계했지만, 항등식이 답을 미리 말한다:
자동 반격은 w_P = w_A = ΔD = 0이므로 **유휴가 정확히 그대로다(62.2%)**.
바뀌는 것은 유휴의 *내용*(내 대신 무언가 일어남)이지 *양*이 아니다.
"가장 값싼 랠리"(조사 §3.7)는 맞지만 **유휴 문제의 답은 아니다.**

### 3.4 [발견] 기믹보다 먼저인 것 — 선공 고정

`g2-winrate-measurement.txt` [OBSERVED]:

```
선공 고정 (출하)   player win rate 87.0 %   G2 band OUTSIDE
선공 교대          player win rate 49.0 %   G2 band INSIDE
first-mover 87.0 % (양쪽 계열 동일)
```

`GameManager.cs:1678` `isPlayerTurn = true`가 플레이어를 **항상** 선공으로 고정한다.
자재·피해가 대칭인데 선공이 87%를 이기는 이유는 단순하다 — 양 진영 성이 같은 속도로
깎이면 **먼저 쏜 쪽이 먼저 도달한다.**

> **⚠️ "49.0% INSIDE"는 시뮬레이터 결과이고 대칭 가정 위에서만 성립한다**
> (`ProgrammerFeasibility` 지적, 채택). 실제 빌드에는 **두 번째 비대칭**이 있다 —
> **AI만 강제 조준 오차를 받는다**: `GameManager.cs:67-68` `aiErrorStart 2.5 / aiErrorEnd 0.8`
> → `:2164` `ai.errorOffsetRange = CurrentAiErrorOffset` 매 턴 주입 →
> `SimpleAI.cs:31`이 표적 좌표에 `Random.Range(-err, +err)` 가산.
> **플레이어측 대응 경로는 0건이다.** 그런데 `SiegePacingSimulation.Run`은
> `aimQuality`를 양 진영 공통 한 줄로 쓰고(`MatchLengthModel.cs:242`) 진영 구분은
> `turns & 1`(`:244-245`)뿐이라 **이 비대칭을 모델링하지 않는다.**
> → 교대를 적용하면 구조적 38 pp는 사라지지만 **실력 비대칭 성분은 남는다.**
> 감도표상 조준 +0.01 = +11 pp이고 밴드 폭(45~55%)이 조준 0.009에 해당하므로,
> **교대 → 재측정 → (필요 시 AI 오차 곡선 조정)** 순서를 밟아야 한다.
> "교대하면 49%가 된다"고 단정하면 안 된다.

**함의 3개:**
1. G2는 기믹 이전에 이미 32 pp 밖이다. 어떤 후보를 채택하든 이 상태에서 측정하면
   결과를 읽을 수 없다. **더 나쁜 것은 측정이 조용히 틀린다는 점이다**
   (`PMRewardCoupling`): 환율 0.534 pp/HP는 **교대 조건(49% 근방, 곡선이 가장 가파른
   지점)** 에서 뽑은 값이다. 87%는 이미 포화 근처라(조준 +0.03 → 90%, +0.05 → 96%)
   거기서 재면 어떤 기믹을 넣어도 델타가 압축돼 **"영향 없음"으로 잘못 읽힌다.**
   → **선공 교대는 밸런스 수정이 아니라 계측 전제조건이다.**
2. **플레이어에게 유리한 비대칭 기믹의 공정성 예산은 9.4 HP가 아니라 음수다.**
   이미 실패 중인 게이트를 더 실패시킨다.
3. 반대로 **뒤처진 쪽에만 주는 기믹은 예산이 양수다.** 43 HP를 뒤처진 쪽에 주면
   43 × 0.534 = **23 pp** 이동한다(87% → 64%). 밴드까지 60 HP가 필요하므로
   **자재만으로는 못 고친다 — 선공 교대가 필요하다.**

코드에 선례가 이미 있다: `BalanceEventPlanner.Plan`(`SiegeTactics.cs:234-259`)이
**코어 체력 격차를 보고 뒤처진 쪽에 버프를 배치**한다(4턴마다, 중립 밴드 0.15).
C1·C2를 이 훅에 얹으면 **랠리 장치 + G2 보정 + G5 컴백 장치가 하나가 된다**(§4.1.7).

> 그 대가가 §4.3.3이다 — **적 턴 입력창을 안 열므로 유휴가 1 pp도 안 줄어든다.**
> C3는 **"할 거리"가 아니라 "볼거리"다.** 디렉터에게 이 한계를 명시해 올릴 것.

#### 4.3.3 유휴 감소 추정

```
w_A = 0, w_P = 0, ΔD = 0, Δ = 0
명목 유휴 = 1 − 5.67/15.01 = 62.2 %          ← 변화 0 pp
```

**결정 밀도**: 22.42 / 283.2 × 60 = **4.75 회/분** (기준 4.19).
**밀도가 오른 것은 반격 때문이 아니라 경기가 짧아졌기 때문이다** (§4.3.4).
반격 자체가 만든 결정은 0이다.

> **§3.3에서 예고한 대로다. D4는 유휴를 못 줄인다.**
> 항등식에 넣을 항이 없다 — 입력도 없고 시간도 안 바뀐다.
> 바뀌는 것은 **적 턴의 내용**이다: "구경"에서 "내 탑이 응수함"으로.
> 이것은 `[INFERENCE]` 영역의 체감 개선이며, 명목 유휴로는 측정되지 않는다.
> **G4 인상 점수로만 검증 가능하다.**

#### 4.3.4 5분 페이싱 영향

**D4는 자재가 아니라 피해를 바꾼다 → 경기를 짧게 한다.**

```
양측 대칭 설치 시:
  내 탑이 적 턴마다 적 코어에 c 피해 → 적 진영 피해 +c × 21.42턴
  상각 피해 d → 37 + c/2

T = 1585 / (37 + c/2) × 7.5 ≥ 270
  → 37 + c/2 ≤ 44.03
  → c ≤ 14.06                    ← 설계 상한
```

| c | d | T | 판정 |
|---|---|---|---|
| 5 | 39.5 | 300.9 s | ✅ 목표 정중앙 |
| **10** | **42.0** | **283.0 s** | **✅ 채택값** |
| 14 | 44.0 | 270.2 s | ⚠️ 수학적 상한 — 여유 0.2초 |
| 20 | 47.0 | 252.9 s | ❌ 하한 위반 |

**상한(14)과 채택값(10)을 가르는 이유 — d 자체가 실측이 아니다** (`PMRewardCoupling` 감도 분석):
`MatchLengthModel.cs:28-31`이 스스로 적는다 — *"The two calibration constants (d and s) are
the honest weak point: they come from **watching play** rather than from instrumentation."*
그 값에 ±오차를 넣으면 상한 근처가 즉시 무너진다.

| c \ d | 36 | **37 (출하)** | 38 | 39 | 40 | d 내성 |
|---|---|---|---|---|---|---|
| **10 (채택)** | 289.9 ✅ | **283.0 ✅** | 276.5 ✅ | 270.2 ✅ | 264.2 ❌ | **+2** |
| 11 | 286.4 ✅ | 279.7 ✅ | 273.3 ✅ | 267.1 ❌ | 261.3 ❌ | +1 |
| 14 (상한) | 276.5 ✅ | 270.2 ✅ | 264.2 ❌ | 258.4 ❌ | 252.9 ❌ | **+0** |

> 식: `T(c,d) = 1585 / (d + c/2) × 7.5`. 반격은 사이클당 1회이므로 턴 평균은 `c/2`다.
>
> **⚠️ 이 표는 개정본이다.** 초판 표는 c=10·c=11 행이 틀렸다 —
> d를 흔들 때 c에도 스케일이 걸려 유효 d가 1단위당 1.82씩 움직였다(정답 1.00).
> `PMRewardCoupling`이 두 레인 표를 대조해 잡았다. d=37 열만 우연히 일치해
> **출하 조건에서는 증상이 안 보였다.** 초판은 자기 라벨과도 모순됐다 —
> 내성을 "+2"로 적어 놓고 셀은 d=39에서 ❌였다.
> **결론은 안 바뀐다**(순위 c=10 > c=11 > c=14, 채택값 c=10). 바뀐 것은 여유의 크기이고,
> 정정 후 c=10은 d=39에서 270.2초로 **간신히 생존**한다(초판은 260.4초로 탈락 표기).
> 즉 **내 산술 오류가 설계를 실제보다 아슬아슬하게 보이게 하고 있었다.**

> **c = 14는 d가 1만 높아도 하한을 깬다. c = 10은 +2까지 견딘다.**
> **수학적 상한 c ≤ 14.06과 채택값 c = 10을 구분해 적는다** — 상한은 유도값이고,
> 채택값은 보정 상수의 불확실성을 흡수해야 한다.

> **⛔ C1과 병행할 때 절대 하면 안 되는 것** (`PMRewardCoupling` 경고, 채택):
> **C1의 활용률 누수(최대 9.35 HP)를 페이싱 예산에 계상하지 마라.**
> 계산상으로는 도움이 된다 — M이 9.35 늘어 c=14에서도 271.8초로 여유가 넓어진다.
> 그러나 **그 9.35 HP는 공정성 예산 전액**이고, 페이싱이 그 누수에 의존하면
> **u_wall이 높아질수록(= 공정해질수록) 페이싱이 깨진다.** 두 게이트가 역방향으로 결합된다.
> u_wall이 100%로 나오면 C1은 공정성 만점인데 T가 270.2초로 되돌아가 c가 다시 벼랑 끝이 된다.
> **두 예산은 독립으로 유지하고, C1의 누수는 항상 0으로 가정하고 c를 정한다.**
> c = 10이면 u_wall이 84.4%든 100%든 양쪽 다 통과한다.

**비대칭이면 상한이 32배 좁아진다** (`PMRewardCoupling`): 누적 c × 21.42가 공정성
예산 9.4 HP를 넘으면 안 되므로 **c ≤ 0.44/턴** — 설계 불가능한 값.
→ **AI 대칭 설치가 선택이 아니라 필수다.**

#### 4.7.2 규칙 정의

```yaml
입력 창: 적 턴 전체 (5.12 s)
방법: 각도만 미리 설정. 궤적 프리뷰 표시.
  ★설계 상한★ 파워는 내 턴에만 조절 가능 — 이유는 §4.7.4 (T 통제)
발사: 불가. 내 턴이 와야 발사. 예약 경로는 Space 커밋 라인을 뺀 별도 함수여야 함

```

#### 4.7.3 유휴 감소 추정

사전 조준이 내 턴 조준 시간의 **절반**을 흡수한다고 본다(D: 5.67 → 4.0).
전량 흡수(D → 3.0)는 §4.7.4에서 페이싱 하한을 깨므로 채택하지 않는다.

```
w_A = 5.12, ΔD = −1.67, Δ = 0
C = 4.0 + 9.34 = 13.34 s
명목 유휴 = 1 − (4.0 + 5.12) / 13.34 = 1 − 9.12/13.34 = 31.6 %     ← −30.6 pp
```

**유휴 저감 2위.** 분자가 커지고 분모가 **작아지므로** 이중으로 유리하다.
결정 밀도: 22.42 / 285.7 × 60 = **4.71 회/분** (커밋 수는 그대로, 경기가 짧아짐).

#### 4.7.4 5분 페이싱 영향

```
D → 4.0 (부분, 각도만)  : C = 13.34 → T = 285.7 초    ✅ 밴드 안, 보정 불필요
D → 3.0 (부분, 더 많이)  : C = 12.34 → T = 264.3 초    ❌ 하한 −5.7 → 보정 +30 HP
D → ~0  (완전 사전조준)  : C =  9.34 → T = 200.1 초    ❌ 하한 −70
```

> **⚠️ C7의 진짜 위험은 F1이 아니라 이것이다** (`ProgrammerFeasibility` 지적, 채택):
> **T가 설계값이 아니라 플레이어 행동의 함수다.** "조준의 몇 %를 적 턴으로 옮기는가"를
> 정하는 것은 설계자가 아니라 플레이어이고, T는 그 비율에 **선형 종속**한다.
> 상한을 규칙으로 박지 않으면 T가 **200~286초 사이 어디에 앉을지 통제 불능**이다.

**게다가 사이클이 줄면 HP 단가도 같이 떨어져 보정이 급격히 비싸진다:**

```
HP 단가 = (C/2) / d
  C = 15.01 → 0.203 s/HP     (기준)
  C = 13.34 → 0.180 s/HP
  C =  9.34 → 0.126 s/HP     ← 같은 1초를 사는 데 HP가 1.6배 든다

완전 사전조준 보정: 270초까지 +555 HP, 300초 목표면 +848 HP = 자재 54% 증량
```

**→ 대응: "적 턴에는 각도만, 파워는 내 턴에" 규칙으로 흡수율을 설계가 강제한다**
(`ProgrammerFeasibility` 제안). 이것이 §4.7.3의 "절반 흡수"를 **가정에서 메커니즘으로**
바꾼다. 초판은 이를 설계 선택으로 적었으나, 강제 장치 없이는 지켜지지 않는 가정이었다.

### 5.2 1순위 근거

**C1을 1순위로 두는 이유는 네 축이 한 점에서 만나기 때문이다.**
유휴 저감이 −34.1 pp로 7개 중 가장 크고(적 턴 5.12초 **전체**를 열기 때문에, 창의 일부만
여는 C2(2.0초)나 조준 시간을 옮기는 C7(−30.6)보다 크다), 참신성은 D3 1/10으로 G8을
통과하며 그것도 castle-war가 이미 가진 유일한 장치 D9(7/10, 최빈)의 정반대편 희소 장치다.
페이싱 비용은 **0이 아니라 구성상 0**이다 — 지연 차감이 ΔM = 0을 보장하고, 적 턴 안에서만
일어나 사이클을 안 건드리므로 §1.2의 0.41초 예산과 §1.3의 43 HP 예산을 **둘 다 한 푼도
쓰지 않는다**. 다른 후보가 이 예산을 놓고 경쟁하는 동안 C1만 예산 밖에 있고, 그래서
**C1은 다른 후보와 병행 가능한 유일한 1순위**다. 그리고 **입력 계층이 이미 작성되어
검증까지 되어 있다** — 지정·취소·고스트·검증·실체화·VFX·알람·리매치 위생·턴 훅이 전부
있고 배치 규칙은 EditMode로 핀되어 있으며, 심지어 `SiegeAlarmSystem.cs:231`이 적 턴마다
"클릭: 벽돌 예약"을 **화면에 띄우고 있다**. 즉 이 채택은 기능 추가가 아니라
**게임이 이미 하고 있는 거짓말을 없애는 일**이며(`QAUxDefects` 프레이밍),
신규 기믹이 통과해야 할 설계 정당화 문턱을 애초에 넘을 필요가 없다.

동시에 이 권고에는 **단서 세 개**가 붙고, 그중 둘은 이 라운드에서 동료들이 내 초판을
반증해 만들어졌다. 첫째, 조사 문서의 "이미 구현되어 있다"는 절반만 참이다 — 구현된 것은
입력 창이고 빠진 것은 경제다. 부울만 뒤집으면 매 턴 Stone 2개(기본값)가 순증해 321초
경기가 **1,059초**가 된다. 원샷 *규칙*은 안 깨지는데(§4.1.7 조건 1~3) 원샷 *페이싱*이
깨진다. 실질 작업은 early-return 삭제가 아니라 **판당 카운터 + 지연 차감 + 회수 역경로 +
AI 미러**이고 앞의 셋은 현재 코드에 0줄이다(`ProgrammerFeasibility` 확인).
둘째, 초판의 "개시 차감"은 **틀렸다** — `PMRewardCoupling`이 보였듯 그것은 적 턴에 손을
안 대는 플레이어에게 확정 60 HP(32.1 pp) 손해를 물린다. 내가 "하는 사람이 세진다"를
막으려 만든 보존이 **"안 하는 사람이 손해"로 부호만 뒤집힌 것**이었고, 지연 차감으로
고쳤다. 셋째, 보존은 총량을 고정하지만 **활용률은 고정하지 못한다**(F8) —
u_wall ≥ 84.4%가 성립해야 5 pp 안에 든다. **그 값은 아직 아무도 재지 않았다.**
**따라서 C1은 "채택 권고"가 아니라 "u_wall 계측을 선행 조건으로 하는 채택 권고"다.**

### 5.3 병행 권고

**C1 + C3.** C3은 유휴를 0 pp 줄이지만 비용이 가장 낮고(대포 재사용) G8을 통과하며
경기를 283초로 **당겨** C1의 걷는 시간 누수(§4.1.4)에 완충을 준다.
C1이 유휴를 줄이고 C3이 적 턴의 **내용**을 채우는 조합이 D3+D4 = **G8 후보 2개**를 만든다.

> **⛔ 병행 시 두 예산을 독립으로 유지할 것** (§4.3.4 상세): C1의 활용률 누수를
> C3의 페이싱 여유로 쓰면 **u_wall이 좋아질수록 T가 나빠지는 역결합**이 생긴다.
> C3의 c는 **C1 누수를 0으로 가정하고** 정한다 → 채택값 c = 10 (d 오차 +2까지 내성).

**C1이 u_wall 계측에서 탈락하면 C7 + C3.** C7은 자재를 아예 안 건드리므로 u_wall 항이
없다 — 조준 시간을 옮기는 것이지 HP를 옮기는 것이 아니다.
**단 "미지수가 없다"는 뜻은 아니다** — C1의 u_wall 자리에 C7은 F6(미러 불가능한 G2
비대칭)이 앉는다. **두 후보 모두 계측 선행이고, 재는 대상만 다르다**:
C1은 u_wall, C7은 선공 교대 후 G2 승률. 대신 C7은 G8을 잃는다.

### 5.4 조건부 1순위

**G8이 다른 경로로 충족되고(N-1/N-2의 QA 인상 점수 ≥4/5) G2 재측정이 통과하면 C7이 1순위다.**
유휴 −30.6 pp를 C1보다 싸게(수정 2파일) 얻고, 자재를 한 톨도 안 늘리며, 페이싱이
285.7초로 밴드 중앙에 가깝다. **조건이 둘이라 C1보다 무거운 조건부**다 —
C1은 u_wall 하나, C7은 G8 + G2 둘. 단 §4.7.4의 흡수율 강제(각도만 사전 조준)가
규칙에 박혀야 하고, 이제 그것은 페이싱뿐 아니라 **F6의 G2 노출을 줄이기 위해서도** 필수다.

   **F8의 u_wall 문턱(84.4% / 89.0% / 93.8%)이 전부 이 선형 가정 위에 서 있다.**
8. **C1의 "판당 2개" 상한은 결정 밀도와 상충한다.** 판당 2개면 21.42 사이클 중
   2회만 새 결정이고 나머지는 재배치다. §4.1.3의 12.18 회/분은 **재배치를 결정으로
   센 값**이다. 재배치가 "결정"인지 "손장난"인지는 QA 인상 점수로만 갈린다.
