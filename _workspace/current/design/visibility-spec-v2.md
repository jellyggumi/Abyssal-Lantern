## 0. 이 문서가 초안과 다른 한 문장

> 초안은 **일곱 개를 더 그리자**고 했고, 조사는 **덜 그리고 대신 이미 일어난 일을

## 1. 조사가 반증한 것 셋

### 1-A. "텔레그래프는 페이싱 예산을 쓴다" → 반대다

Into the Breach 개발 기록: *"telegraphing the Vek's movements further **helped to
hasten the pace**"* `direct page retrieval`. 300초 밴드는 텔레그래프의 **제약이
아니라 근거**다.

**단, 이것이 우리에게 사전 예고를 정당화하지는 않는다** — 아래 1-C를 보라.
초안이 반박한 이유가 틀렸다는 것이지, 초안의 결론이 옳았다는 뜻이 아니다.

### 1-B. "UI를 더 그리면 보인다" → 검증된 실패 경로다

같은 팀의 자백: 놓치는 플레이어가 나올 때마다 아이콘을 추가한 결과 *"1년 반 전
게임은 그냥 아이콘 쓰레기장이었다"*. 그들의 해법은 **표시 추가가 아니라 메커니즘
삭제**였다 — *"we would sacrifice cool ideas for the sake of clarity every time"*.

초안 §1-B는 플레이스홀더 7종을 만들었다. 그중 **6종은 이 문서가 취소한다**(§5).

### 1-C. "적 사전 예고를 넣자" → 성립 조건 불충족

사전 예고가 성립하려면 두 가지가 필요하다.

| 조건 | ItB | castle-war |
|---|---|---|
| 대응 가능성 | 이동·밀치기·방어 | **없음 — 적 턴 입력 0** |
| 정보 창 | 내 턴 전체 | **0.9초** |

ItB 원문이 예고의 목적을 *"내 턴에 적의 계획을 교란하는 것"*이라 밝힌다.
**교란 수단이 없으면 예고는 목적을 잃는다.** 그리고 과잉 예고의 청구서도 관측된다 —
ItB Steam 부정 리뷰 *"전략이 아니라 퍼즐"*(+11).

## 2. 성립하는 것: 사후 판독 — 선례는 Rampart(1990)

| | 사전 예고 | **사후 판독** |
|---|---|---|
| 정의 | 적이 쏘기 **전에** 의도 공개 | 적이 쏜 **뒤에** 무엇이 왜 왔는지 남김 |
| 대응 수단 | **필요** (없으면 무력감) | **불필요** |
| 다음 결정에 쓰임 | 이번 턴에 못 씀 | **다음 턴 조준에 직결** |
| 1차 선례 | ItB·StS | **Rampart(1990)** |
| 클러터 위험 | 높음 | 낮음 — **사건 자체가 표시다** |

Rampart는 우리와 구조가 거의 같다: 성 대 성 + 대포 + 부서지는 벽 + 교대 페이즈,
그리고 **적의 사전 예고가 전혀 없다.** 플레이어가 소비하는 정보는 *적이 쏜 뒤 벽에
남은 구멍 패턴*이고, 그것이 다음 건설 결정을 지배한다. CVG 93%, 타워디펜스 장르의
조상 `direct page retrieval`.

판독 시점은 Worms가 이미 못박아 놓았다 — 피해 보고는 *"after any player's turn,
**when all movement has ceased**"*. 0.9초 창에 욱여넣을 필요가 없다는 뜻이다.
우리 코드에는 그 지점이 이미 있다: `GameManager.WaitAndEndTurn`의 정착 루프 종료
(`GameManager.cs:2226`).

### 왜 우리에게 특히 맞는가

> **castle-war는 은폐의 비용만 내고 수익은 이미 반납했다.**

포병 계보(Worms·Gunbound·포트리스2·Scorched Earth·ShellShock·GunboundM,
적 정보 장치 `[OBSERVED 0/6]`)가 적 정보를 감춘 이유는 **조준 추정 자체가 실력
축**이었기 때문이다. 우리는 그 실력 축을 스스로 전부 제거했다 — 궤적 프리뷰가 실전
물리와 동일하고(작업 #33), 발사체는 선택이 아니라 규칙이며, 한 턴에 한 발이다.
**은폐가 지킬 실력 축이 남아 있지 않다.** 남은 것은 경기의 34.1% 동안 볼 것이
없다는 비용뿐이다.

## 3. 판독의 3층 — 우리는 가운데 한 층만 갖고 있다

조사(`actual-lane-c.md` §D-4)가 흔적 판독을 3층으로 나눈다.

| 층 | 장르 이력 | castle-war 현재 |
|---|---|---|
| 1 — **궤적 흔적** | 1980년부터, tracer로 상품화 | **비행 중에만 존재, 착탄과 함께 소멸** |
| 2 — 지형/구조 흔적 | Worms 영구 변형, Rampart 벽 구멍 | **보유** (구조 붕괴는 남는다) |
| 3 — **수치 판독** | Worms: 움직임 정지 후 전 턴 보고 | **없다** |

공백은 1층과 3층이다. 2층은 이미 있으므로 건드리지 않는다.

### 1층이 왜 비었는지는 코드가 말한다

```
UnitController.cs:482   trailRenderer.time = 0.5f;
UnitController.cs:1174  trailRenderer.emitting = false;   // 착탄 시
```

**트레일은 시간축이 없다.** 팀색·굵기·Barrel 구분은 이미 있다(`:483-490`) — 조사
Lane D가 자기 초판 권고("탄종별 색 구분")를 스스로 철회한 지점이다. 색은 문제가
아니었다. **여러 샷에 걸친 조준 학습이 축적되지 않는 것**이 문제다.

## 4. 만들 것 — 셋

### R-1. 샷 궤적 잔존 (1층)

발사체가 실제로 지나간 경로를 **착탄 후에도 남긴다.** 다음 샷이 커밋될 때 지워진다.

| | |
|---|---|
| 무엇 | 비행 중 표집한 위치를 선으로 그대로 남긴 정적 아크 |
| 언제 | 착탄(또는 소멸) 순간부터 **다음 발사 커밋까지** |
| 누구 | 양 진영 — 적 샷만 남기면 내 샷과 비교가 불가능하다 |
| 색 | 기존 트레일 팀색 그대로 (`(0.45,0.85,1)` / `(1,0.35,0.25)`), 알파 감쇠 |
| 이미지 | **없음** — LineRenderer |

내 직전 샷과 적 직전 샷이 **동시에 화면에 있다.** 그것이 조준 학습의 단위다.

### R-2. 탄착 마커 (1층)

궤적의 결론을 점 하나로 찍는다. **초안에서 유일하게 살아남은 요소**다 — 궤적선은
이미 정확한데 *어디에 맞는지*를 명시하지 않는다.

| | |
|---|---|
| 무엇 | 마지막 궤적점에 놓이는 마커 |
| 언제 | R-1과 같은 수명 |
| 이미지 | `ui_ph_impact_marker.png` (플레이스홀더, 128×128) |

### R-3. 턴 판독 한 줄 (3층)

Worms 규약대로 **움직임이 완전히 멈춘 뒤** 한 줄을 남긴다.

```
적 화약통 → 성벽 3블록 파괴 · 코어 -40
적 기사   → 빗나감
```

| | |
|---|---|
| 무엇 | 직전 턴이 무엇을 쐈고 무엇을 부쉈는지 |
| 언제 | 정착 루프 종료 직후 (`GameManager.cs:2226`), 다음 턴 시작까지 |
| 어디 | 기존 `flowStrip` 자리 — **새 자리를 만들지 않는다** |
| 이미지 | **없음** |

**이것이 "적이 어떻게 쏘는지 안 보인다"에 대한 직접 답이다.** 적이 무엇을 노렸는지가
아니라 **무엇을 했는지**를 말한다. 후자는 대응 수단을 요구하지 않고, 다음 턴 조준에
실제로 쓰인다.

## 5. 지울 것

### 5-A. 거짓 지시 2건 — 최우선

표본 12종 중 **작동하지 않는 지시를 표시하는 게임은 0개다.** 이건 가시성 부족과
다른 결함 등급이다.

| 결함 | 현재 | 조치 |
|---|---|---|
| UX-003a | `SiegeAlarmSystem.cs:225`가 적 턴마다 `클릭: 벽돌 예약`을 띄우는데 `BrickPlacementController.cs:76-82`가 그 클릭을 막는다 | **문구를 조건부로** — 지정 창이 실제로 열려 있을 때만 |
| UX-003b | `LaunchManager.cs:121`의 발사 안내가 적 턴에도 남는다 | 적 턴·해결 중에는 숨긴다 |

**기능이 없는데 안내가 있는 것은 안내가 아니라 함정이다.**

문구를 지우는 대신 **게이트를 읽게** 만든다. 리터럴로 지우면 기능이 켜질 때 안내가
안 돌아온다 — 작업 #49가 좌표 리터럴로 겪은 것과 같은 종류의 노후화다.

## 6. 배치

새 자리는 **하나도 만들지 않는다.** R-1·R-2는 전장에 그려지고, R-3은 기존 스트립을
쓴다.

```
┌──────────────────────────────────────────────┐
│ WIND ...        [턴 라벨/타이머]      SIEGE  │  상단 — 변경 없음
│ 보급 …                                SCORE  │
│           [KEEP CORE]  [BREACH CORE]         │
│                                              │
│      ╱‾‾╲___                                 │  R-1 내 직전 샷 (청)
│   ╱        ╲___ ◉ R-2                        │
│  ‾‾╲                                         │  R-1 적 직전 샷 (적)
│      ╲__ ◉                                   │
│                                              │
│  [적 화약통 → 성벽 3블록 · 코어 -40]          │  R-3 = 기존 flowStrip
└──────────────────────────────────────────────┘
```

- R-1/R-2는 월드 스페이스 — HUD 캔버스 이슈와 무관
- R-3은 기존 `flowStrip`을 재사용하므로 `HudCanvas.Resolve()` 규칙을 이미 만족
- 정렬 순서: 궤적 `sortingOrder` 2 (기존 트레일과 동일), 마커 3

### 이 작업이 통과시키지 못하는 것

조사가 정직한 공백을 하나 기록했다:

> **아무도 "플레이어가 적 사격을 못 읽는다" → "흔적을 추가한다" → "불만 해소"의
> 인과 사슬을 문서화하지 않았다.** 흔적은 46년 된 장치지만, 그것이 *우리* 불만을
> 해소한다는 것은 **가설**이다.

따라서:

- **G4(몰입) 인상 점수 ≥4.0/5는 이 작업만으로 통과하지 않는다.** 판독은 몰입의
  전제이지 몰입 자체가 아니다.
- **유휴 62.2%는 1%p도 줄지 않는다.** 보는 것은 입력이 아니다. 랠리는 다음 사이클
  C1/C7이고, 그 앞에 M1(선공 교대)이 있다(`production/research-to-change-ledger.md` §4).
- **재미가 늘어난다고 하지 않는다.** 읽을 수 있게 될 뿐이다.
